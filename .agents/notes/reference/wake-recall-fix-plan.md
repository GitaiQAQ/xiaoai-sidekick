# Reference: Wake-word recall investigation

记录日期：2026-11-02。状态：调优进行中，尚未完成现场可用性验收。

## 用户遇到的问题

用户反馈：喊“豆包豆包”大概率没有回应，当前无法正常使用。优先目标是提高真人正常呼叫的命中率，同时避免重新引入音乐无人呼叫时的自激活。少数成功对话不能代表唤醒已经可用。

## 已确认的情况

- 已安装并启动原厂格式自有模型：一级 d96-v5、二级 l2-d160，通过音箱原厂 Rice/Paddy 引擎运行。B共享类别版本未安装。
- 现场已有一级候选被二级拒绝的日志，也有少数flag1确认后本地“收到”、云端会话和回答播放成功。因此缺凭据、服务未启动或回应文件缺失不能解释所有漏检；但每次失败仍需按输入、一级、二级、播放逐层区分。
- 原厂引擎离线回放s3真人音乐录音240秒有8次确认；两段纯音乐共480秒候选/确认0。这是有限样本回放，不是现场召回率或长期误唤醒验收。
- 无Key本地待机已实现；确认后播放“收到”和缺配置提示、不连接云端。无Key播放测试用手动触发，不是独立现场关键词验收。
- B方案同口径测试：合成正例25/38（v5为30/38），s3合并句17/35，纯音乐s2b仍3次误触发，体积仍639597B；不据此替换现有部署。

## 阈值是什么，为什么不能直接随便改

神经网络输出声学类别分数，解码器结合关键词顺序、路径及时间限制决定是否唤醒。放宽判定可以提高召回，但会增加误接受。召回下降指真正喊词时漏掉更多，不是播放音量变小。

当前有至少三类数值，不能混用：网络声学分数、Mac参考Viterbi margin、原厂Rice日志score。Mac阈值0不是音箱可直接写入的参数。

部署代理本轮初步静态核对（尚待实测）：conf的--score-threshold解析到state+0x3e8，默认1；当前分析到的Viterbi路径主要减prior，IsKeyword检查最终token的关键词字段。已有score0.097/0.204也产生候选或确认，故不能断言日志score必须大于1。二级判定还涉及循环帧数1/80、等待60帧、缓存边界和路径竞争。静态覆盖尚不完整，不能断言score-threshold完全无效。

## 具体解决步骤

1. 保留实时诊断：明确模型ready、实际采集帧数/峰值/均方、一级候选、二级超时或确认及ack播放。只记录元数据，不保存新录音，不输出凭据。
2. 验证阈值旋钮：通过重打包模型conf设置少量候选score-threshold，隔离probe读回参数并比较相同fixture的原厂输出。未知偏移不写生产进程。
3. 在同一套数据对比召回与误触发：s3用现有人工标签，区分片段与严格间隔<0.5秒的合并句；s2b作为保留纯音乐负例，s2注明参与训练。若用这些数据选择参数，结果属于调参验证，后续仍需独立现场验收。
4. 若score-threshold不能有效改善，定位路径、时长/缓存或二级模型的拒绝原因，再针对已证实原因调整。不能直接绕过二级，也不能仅凭更大的日志分数认定正确唤醒。
5. 将有改善且误触发可控的候选先在Mac/隔离设备验证，再部署；恢复材料放Mac private/deploy-recovery/，音箱不累积历史备份。PCM只从Mac流式回放，避免/tmp占RAM引发OOM。
6. 现场验收分别覆盖安静和播放音乐，记录总呼叫数、成功数、延迟及无人呼叫事件；目标先由用户体验确认，不能提前承诺百分比。现场失败继续根据分层日志归因。

## 当前证据边界

已实测：此前部署与有限回放结果、部分现场一级候选/二级拒绝及成功对话、B模型对比。

待验证：score-threshold的实际作用、最佳设置、放宽后独立现场召回及长时间音乐误触发。尚未证明仅调整一个阈值就能解决问题。
