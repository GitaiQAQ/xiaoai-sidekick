# Reference: 唤醒阶段分流：小爱与豆包共存

用户提出从唤醒入口分流，让两套助手共存。该方向比监听ASR后抢答更适合保留原厂能力，但本机尚未实现。

目标：小爱同学->原生链；豆包豆包->新豆包会话。原厂小米服务常驻，豆包会话不全局禁用原拾音/网关。

核对本地源码：
- examples/kws/README.md 已给出“豆包豆包”自定义唤醒词。
- 同文明确提示：上游仅在OH2P和256MB LX06等机型测试；128MB新版LX06可能Killed，无法加载该KWS服务，建议外部Server。该建议不符合本项目“不用额外常开设备”的约束，故不能直接部署示例。
- 文档描述部署存储约20MB，当前/data空闲约8.2MiB也不足直接照搬。
- packages/client-rust/src/bin/monitor.rs 的on_keyword最终调用 pnshelper event_notify src=1,event=0，实际仍唤醒原小爱；这不是豆包独立会话实现。
- monitor/kws.rs监听的/tmp/open-xiaoai/kws.log是开源KWS服务生成的事件，不是已验证可获取的原厂唤醒结果。

推荐研究优先级：
1. 研究原厂唤醒引擎是否支持第二唤醒词及独立标识/回调，可能复用已有模型，资源最省；尚无证据可行。
2. 若不支持，选更小的单关键词检测器或裁剪模型，在PC先核算模型体积和ARM ABI，再在本机测RSS/峰值CPU。不能因为“小模型”三个字就假定满足128MB约束。
3. 在新唤醒入口中创建豆包会话；不调用上游示例唤醒原小爱的动作，使用已验证共享录音并直连云端。
4. 用单一音频仲裁器处理小爱/豆包/音乐/闹钟/通话，检测“小爱同学”切回、退出豆包、硬件静音与取消上传。具体优先级需实测。
5. 后续验证豆包工具调用原生米家文本入口；双唤醒只能解决入口归属，不会自动提供家电控制。

状态：仅架构与源码核对，未安装KWS、未改配置或开启常驻采集。
