# Agent Note: Music-mode wake stopped firing after the AEC integration

Status: implemented

## Problem

当前限制：用户继续报告无人呼叫时反复自激活。[第二十三轮复核](../../reports/music-trigger-and-factory-wake-review.md)证明候选暂停后的重叠窗口仍会重复认可旧音乐，且存在绕过暂停的判醒。本笔记记录已部署的三项修正及其来由，不代表音乐下误激活已经解决；两次判醒仅能证明流程曾被触发。

AEC 接入采集路径后，音乐播放中说“豆包豆包”仍然唤不醒。日志显示语音窗口距离 13.8–15.3，阈值 12.5048；纯音乐窗口在 11–13 之间随路径和音量变化。现场排查定位到三个叠加成因；未做穷尽的逐项回退实验，不能据此断言每一项在所有场景下都独立导致失败：

1. 采样率控制取错了符号。本机 `libspeexdsp.so.1.5.0` 导出 `speex_echo_ctl`，代码找的是 `speex_echo_state_ctl`，于是从未执行 `SPEEX_ECHO_SET_SAMPLING_RATE`，AEC 一直按默认 8 kHz 配置处理 16 kHz 数据。
2. 麦克风只用 ch0。同段语音经 AEC 加预处理后最低距离为 12.05，六麦混音为 11.66。12.05 实际低于 12.5048，但单麦余量更小；最低距离过线也不等于满足连续窗口确认。
3. AEC 生效时把候选暂停关掉了。代码只在“第 3 个命中且尚未唤醒”时暂停音乐，而音乐模式又要求 3 连击唤醒，条件永远不成立；音乐残留与语音距离重叠，固定阈值无法两边成立。

## Decision

三个修正作为同一套已验证配置保留：

- 用 `speex_echo_ctl(st,24,&16000)` 设置采样率，并回退查询 `speex_echo_state_ctl`；启动日志输出 `capture_speex_rate=16000`，回归时先看这一行。
- 麦克风输入取 ch0–ch5 的平均，ch6 继续作播放参考。
- 音乐播放且 AEC 生效时：阈值 15.0，连续 2 个窗口命中就暂停原厂播放器 2.2 秒，用干净音频完成第 3 个确认窗口；未确认则恢复播放，候选暂停有 6 秒冷却。静音环境仍是 12.5、3 连击。

同次采集内各路径使用同一段输入；说话与只放音乐分开测量。距离越小越接近模板，诊断阈值为 12.5048。以下数据汇总自[第二十二轮报告](../../reports/capture-path-echo-cancellation-integration.md)，不是所有单元格都来自同一次采集：

| 路径 | 说话 | 只放音乐 |
|---|---|---|
| ch0 原始 | 9.24 | 12.57 |
| ch1–ch5 原始 | 9.60–9.96 | 10.97–12.60 |
| 6 麦混音原始 | 8.97 | 11.26 |
| ch0 + AEC + 预处理（采样率已修正） | 12.05 | 14.55 |
| 6 麦混音 + AEC + 预处理 | 11.66 | 14.62（音量 30）/ 13.41（34）/ 19.34（17） |
| ch0 + AEC，未设采样率 | 13.28 | — |
| ch0 + AEC，采样率 16000 | 9.57 | 14.57 |
| 6 麦混音 + AEC，无预处理 | 8.85 | 11.03 |

部署后两次真人唤醒在候选暂停后以 12.5082、14.6845 确认，会话建立并恢复播放；线上音乐模式阈值为 15.0，不能用诊断阈值 12.5048 判断这两次是否过线。详细过程见 [第二十二轮报告](../../reports/capture-path-echo-cancellation-integration.md)，采集实现见 [Speex echo cancellation for the capture path](../architecture/2026-11-01-speex-aec-integration.md)，测量方法见[同音频采集 A/B](../testing/2026-11-01-capture-ab-comparison.md)。

## Consequences

- 唤醒在音乐下恢复可用，代价是每次候选都让音乐停顿约 2.2 秒；一个实例里出现过 2 次未确认的暂停，频率需要长期观察。
- 语音距离和音乐残留的余量只有 1–2 个点，音量越高余量越小；高音量与远场的召回仍未验证。
- 这三个参数不要单独回退：采样率符号与 16 kHz 设置、六麦混音、候选暂停。重引入旧方案或替代实现前，必须验证有效采样率与启动日志，用 `--mic-compare` 分别测纯音乐安全余量和真人召回余量，再以真实播放状态验证候选暂停、连续窗口确认、会话建立和播放恢复；同时记录音量、站位及误暂停。仅有更低 RMS、某一窗距离改善或纯音乐零唤醒，不满足重新评估条件。满足这些条件后再决定是否替换整套配置，不声称所有单项回退均已实测。
- 预处理保留。它让语音距离变差约 2.5，但去掉后纯音乐距离降到 10–11，会持续误唤醒。

## Alternatives considered

- **只把全局阈值提到 15**：纯音乐在音量 30–34 时已经到 13.4，不暂停就会误唤醒，无法只靠阈值区分。
- **去掉预处理保护语音**：语音变好但音乐下纯音乐距离降到 11.0，误唤醒明显增加。
- **保留 ch0 并降低阈值**：降低距离阈值会收紧召回，无法解决漏唤醒；不能把 ch0 原始纯音乐的 12.57 与 ch0 AEC 加预处理的语音 12.05 当成同一路径的间隔。
- **用扬声器播放唤醒录音来验证**：AEC 会把这段声音当参考信号抵消，测试无效，必须真人发声。
- **只在待机时放宽阈值、不做暂停确认**：音乐残留本身就会越过放宽后的阈值，误唤醒与漏唤醒同时存在。
