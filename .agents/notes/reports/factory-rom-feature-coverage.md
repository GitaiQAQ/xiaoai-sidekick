# Report: Factory ROM Product Feature Coverage

## Goal and completion rule

This is the coverage ledger for reverse engineering product-facing behavior in the LX06 factory ROM used by this project. The target build is firmware 1.94.13 on system0 unless a row says otherwise. The goal is broader than the 35 Sidekick tools and broader than the currently published ubus surface: classify every product feature entry point found in services, executables, libraries, scripts, local IPC, and firmware configuration, then trace its implementation and protocol.

A feature is complete only when the ledger links evidence for its entry point, implementation path, input/output contract, state effects and authorization boundary. Record what cannot be recovered and why. A string, exported symbol, ubus signature, or successful process exit is a lead, not proof that a feature works. Keep static evidence, measured behavior, public sources, inference and unknowns distinct. Never read or publish account credentials, authentication material, Mesh keys, user databases or personal content for this work.

## Inventory baseline

The current local extracted rootfs is `temp/rootfs-factory-full/`. A filesystem enumeration on 2026-11-03 found 55 regular files under `etc/init.d/` and 248 regular files directly under `bin/`, `sbin/`, `usr/bin/` and `usr/sbin/` (41, 19, 126 and 62 respectively). A content-signature scan classified those 248 files as 169 ELF objects (11, 12, 100 and 46 per directory), 76 shebang scripts (29, 7, 25 and 15) and 3 other files; the local extraction has normalized permissions, and all 248 currently lack executable mode, including known ELF binaries. Do not use mode bits to establish ROM executability. The 55 init scripts have provisional role rows; the 76 non-init shell scripts have a 76/76 provisional triage against the local files. A separate ELF type scan found 258 objects under `/lib` and `/usr/lib`: `/lib` has 66 `ET_DYN` objects and 54 `ET_REL` kernel modules under `lib/modules/4.9.61/`; `/usr/lib` has 137 `ET_DYN` objects and one `ET_EXEC` D-Bus helper. Thus the total is 203 dynamic objects, 54 kernel modules and one helper, not 258 shared libraries. Their provider/consumer roles and module-loading conditions are not yet fully mapped. The extracted tree currently contains no symlink entries, which likely means alias/target metadata was not retained and must not be assumed absent from the source ROM. Four regular UCI config filenames are present (`bluetooth`, `dhcp`, `dropbear`, `network`); values were not read. These are path counts, not feature counts; dynamically loaded modules and data-driven behavior need separate classification. The target device's read-only runtime inventory found 26 ubus objects and 260 method signatures. These interfaces overlap and do not cover private IPC or cloud behavior.

The 55 init script names at baseline are: `adbd`, `alarm`, `alsa`, `bluetooth`, `bluetooth_aplay`, `bluetooth_ble`, `bluetoothd`, `boot`, `boot-test-end`, `boot-test-start`, `central_lite`, `coredump`, `cron`, `dbus`, `dhcpc`, `dhcpc_p2p`, `dhcpd`, `dlnainit`, `dnsmasq`, `done`, `dropbear`, `gpio_switch`, `idmruntime`, `led`, `linein`, `logrotate`, `mediaplayer`, `messagingagent`, `mibrain_service`, `mibt_mesh`, `mico_ai_crontab`, `mico_aivs_lab`, `mico_helper`, `mico_ir_agent`, `miio`, `miio_agent`, `miio_client`, `miio_mpkg`, `miplay`, `nano_httpd`, `odhcp6c`, `odhcpd`, `pns`, `pns_ubus_helper`, `quickplayer`, `silentboot`, `sound_effect`, `statpoints_daemon`, `sysctl`, `syslog-ng`, `touchpad`, `umount`, `urandom_seed`, `voip`, and `wireless`.

## Mesh proxy envelope (static)

Static analysis of `miio_helper` closes part of the local IPC envelope: it creates an `AF_UNIX/SOCK_SEQPACKET` client connection to `/tmp/mibt_mesh_proxy.sock`, then uses `ustream_fd` callbacks and an incremental JSON tokener. Its dispatcher correlates integer `id` values against pending responses; unmatched parsed objects are inspected for string `method` and object `params` and sent to a local method handler. The write callback sends the provided buffer as-is without a newline. The daemon reads up to 8192 bytes, tags the payload in a 76-byte event record (`4`, `1` at offsets 0 and 1), then passes it to internal handler `0x81cfc`.

This is direct static evidence for the JSON field names and client routing structure. It does not recover required fields, the handler allowlist, method-specific parameter schemas, response/error result bodies, or successful end-to-end behavior. Client `ustream_read` chunks up to 4096 bytes while daemon `read` uses an 8192-byte buffer; truncation and multi-packet behavior have not been tested. Do not connect to this socket or send speculative payloads as part of routine reverse engineering.

### Factory ROM `mibt_mesh_rtl` cross-check

The factory rootfs copy at `temp/rootfs-factory-full/usr/bin/mibt_mesh_rtl` has the same two method-table file offsets (`0x1f5cbc` and `0x1f5dc4`; corresponding VMAs `0x215cbc` and `0x215dc4`) and method-name families as the separately examined active ELF, but the handler pointers differ. Examples from the factory copy are `_local.open_mitv` → `0x8d28c`, `_local.disable_gateway` → `0x84d78`, `_local.miot_device_scan` → `0xb27d4`, `_local.miot_bind_device` → `0xb2bf0`, `get_properties` → `0xaade8`, `set_properties` → `0xab778`, `action` → `0xac374`, group methods → `0xb02e8–0xb0300`, and scene methods → `0xb0308`, `0xb09cc`, `0xb0de0`, `0xb109c`. These are factory-copy VMAs, not active-runtime addresses. The table layout and names therefore support a shared dispatch-family lineage, while the code addresses and behavior cannot be substituted across versions. The active ELF is a distinct binary and is not present in the current extracted rootfs tree for a same-file byte comparison.

Static disassembly of the factory copy shows a registration helper iterating 8-byte name/handler records, with caller-selected table/count pairs including 96, 32 and 128 entries; the 32-entry path references the table at `0x215cbc`. This confirms table consumption by code, though not the semantics of every registration type or the exact table termination convention. The factory copy's handler table adds no recovered field-requiredness, JSON types/ranges, reply/error mapping, payload-size bound, or authorization provenance. Existing `did`/`siid`/`piid`/`value`/`tid` field clues and product-rule-dependent behavior remain static leads only. Scan, bind, property, group and scene state effects are not validated by a request or device observation. Both copies are analyzed statically; no program, socket, device or network was used.

## MiIO local RPC and provisioning (static)

The `miio_agent` init script starts `/usr/bin/miio_agent -l 4` under procd with respawn. The daemon creates an `AF_UNIX/SOCK_SEQPACKET` listener at `/tmp/miio_agent.socket`, binds a Unix address, listens with backlog 32, and accepts clients through an epoll-driven path. Its parser extracts JSON `id` and `method` fields and checks an internal request queue before dispatch. This resembles a local message-RPC service, but required fields, `params` schema, response/error format and pending-ID behavior have not been fully recovered; do not call it JSON-RPC based on field names alone. `agent_client` and `agent_sendline` contain the same socket path and socket/connect/send imports, but they were not executed.

The `wireless` init script exposes actions for Wi-Fi, config mode, scan preparation/restoration, AP/STA lifecycle and MiIO registration. `bind_device.sh` waits for UID availability, checks an unbind-in-progress marker, requests `mibt.ble` hidden mode, ensures a config-done marker, then invokes a MiOT-token download/sync command. No UID, token or credential value was read. The registration message and failure contract remain unresolved.

The static `unbind_device.sh` path marks an unbind-in-progress flag, performs unregister cleanup, stops wireless and contains a broad `/data/*` deletion path followed by reboot. This is destructive code behavior, not a claim that it was invoked or that it is equivalent to factory reset. It must remain an unexecuted high-risk entry point. No device or cloud calls were made in this analysis.

### MiIO-agent local socket dispatcher (static)

The `miio_agent` JSON handler is at VMA `0x12404`; it reads up to 1024 bytes, parses JSON and extracts `_to` and string `method` around `0x1248c–0x124b4`. Three explicit router-control branches compare `register` (VMA `0x12510`), `unregister` (`0x12528`) and `bind` (`0x12548`): registration operations require a string `key`, while bind requires integer `address`. Error strings include invalid method/key/id/address and key not found. The bind path maps an address into internal address/bitmap state associated with a client fd.

The generic path extracts integer `id`, rewrites or substitutes the identifier, removes `_to`, appears to attach `_from`, and forwards the JSON to a registered client fd. Log strings record new/old IDs and fd; the complete reverse-response correlation and timeout behavior remain unknown. The daemon imports socket/bind/listen/accept/epoll/read/send/timerfd and has a `session timeout` string. No exact `params` or `result` key was found, so this must not be described as standard JSON-RPC. The explicit `register/unregister/bind` branches look like router/session control rather than a recovered product-feature allowlist; that classification is an inference.

`miio_helper`, `agent_client` and `agent_sendline` contain the same socket path and socket client imports, but their exact envelopes/callers remain untraced. `miio_helper` also imports Wi-Fi provisioning, ubus, token and bind-key related APIs; API presence alone does not map a specific socket message. The `wireless` `miio.connect`/`miio.config_mode` ubus methods are a separate interface layer from these socket router controls. `bind_device.sh`'s `mibt.ble(action=hidden)` and token-sync hook also lack a proven mapping to an agent-socket method. No socket was connected and no key/token values were read.

## Central Lite, IDM and local discovery paths (static)

`central_lite` creates `/tmp/central_service_lite.socket` as an `AF_UNIX`, `SOCK_SEQPACKET|SOCK_NONBLOCK` listener, then unlinks, binds and listens on the path (VMA about `0x17808–0x178b4`; path string file offset `0x122c12`). `mibt_mesh` creates an `AF_UNIX/SOCK_SEQPACKET` client socket (VMA `0x34594`) and calls `connect` (VMA `0x346c8`) to that same path (string file offset `0x164934`). This confirms local IPC between those two binaries; it does not establish LAN/cloud transport.

## Initial physical-control review (static)

### `miio_agent` local request routing (static ARM analysis)

The dispatcher reads at most 1024 bytes per request. Requests with integer `_to` enter the forwarding path: the daemon removes `_to`, inserts `_from` as the sender's slot index, replaces the integer `id`, records the original sender fd/id, and sends to live slots selected by testing the destination value as a bitmask across 32 slots. The bitmask interpretation follows the slot loop and bit tests; the binary provides no protocol documentation. A reverse message with a matching rewritten `id` has that id replaced by the recorded original id and is returned to the original fd, after which the pending record is removed. The pending record owns a 5000 ms timer; timeout paths clean it up and log, with no client-visible timeout reply observed. Reverse messages with no pending ID appear to be broadcast to connected slots, inferred from the fallback loop. The control-method branch recognizes `register`, `unregister`, and `bind`; `register` requires string `key`, `bind` requires integer `address`. These field types do not establish authorization or key/address semantics. No local socket was opened and no request was sent.

### Touchpad SSH-enablement sequence (static ARM analysis)

`bin/touchpad` reads 16-byte Linux input events from `/dev/input/event0` and `event1`, masks bit `4` from the event type, and continues only for `EV_KEY` (`type == 1`). The key event value at offset 12 is then checked: the DFA branch is reached only when `value == 1` (key down); release events do not advance the sequence. The compiled DFA table at VMA `0x2310c` has length 8 and expected key codes `[102, 102, 114, 114, 115, 115, 139, 139]`, which map in this binary to mute, play, volume-down, volume-up twice each. A successful full match calls the callback pointer at state offset `+0x1c`; its initialized target resolves to PLT `sys_ssh_enable`, matching the `ssh enable` state label. The DFA compares elapsed time using imported `difftime` and a double constant `60.0`; when elapsed time exceeds 60 seconds it logs timeout and resets the index. A wrong key also resets the index and refreshes the start time. This recovers a hidden SSH-enablement gesture from code, not evidence that a physical device received it or that SSH was enabled during this analysis. Other key-state interactions, debounce behavior, and whether all hardware revisions expose these key codes remain unknown.

The local source review of `etc/init.d/touchpad`, `led`, `silentboot`, `gpio_switch`, and `alsa`; `etc/rc.button/{power,reset,rfkill}`; `bin/{touchpad,ledserver,show_led}`; and `usr/bin/sys_power_down.sh` found:

### OTA image validation and dual-slot details (static)

`bin/miso` is an ARM EABI5 ELF linked to OpenSSL crypto. Imports include `PEM_read_bio_PUBKEY`, `EVP_VerifyFinal`, `EVP_sha1`, `EVP_sha256`, `RSA_public_decrypt`, AES-128-CBC and MD5 APIs. Format/error strings identify `rsa + sha256` and `rsa + sha1` validation paths, checksum and outer/segment magic checks, model mismatch, encrypted-image handling and `encrypt_info_decode`. Metadata vocabulary includes model, segment, offset, flash address, length, partition, and subheader magic/`le_mag`/`rsvd0`. The exact header layout, field widths/order, checksum algorithm, algorithm selection, and trust-root/key source remain unknown. No key or certificate was extracted or read. The utility reads `/proc/mico/model` for model matching; the accepted model map is incomplete. `miso.ko` registers a character device corresponding to `/dev/miso`, but ioctl command/argument contracts are unresolved.

Observed static CLI forms include `miso -v` verify, `miso -c -f <segment>` check-segment and `miso -r -x -f <segment>` extract; `-n` and remaining options are unresolved. `ota`'s `verify_upgrade()` is empty and has no discovered caller; the active script validation gate is in `flash.sh:99–113`, which runs `miso -v` before stopping services, falling back to `mkxqimage -r -v` only when `miso` is not executable.

`boardupgrade.sh` selects the alternate boot/system slot from `boot_part`, writes kernel/rootfs segments there, and changes `boot_part` only after segment steps report success. It does not show a read-back verification of written contents or verified success from the slot-change command. Optional DTB writes target `/dev/dtb`; optional bootloader/TPL segments are written to fixed offsets in shared partitions outside the A/B kernel/rootfs slots. These shared writes weaken the protection provided by dual slots if interrupted. No startup health check or automatic rollback is visible in this script; other bootloader/kernel recovery behavior is unknown. The model-check helper is an empty function; missing DTB can be skipped, and bootloader update can report success while skipped for missing segments or `nandwrite`.

Generic `/sbin/sysupgrade` is separate from vendor OTA: it runs `fwtool_check_image` and `platform_check_image` before `upgraded`; `--force` can bypass an image-check failure. `EnterFactory` is a fixed boot0→boot1 factory mount/switch/reboot path with no ordinary product caller found. The cryptographic meaning and exact fields checked by those tools remain unknown.
- The OTA script downloads to `/tmp/mico_ota.bin`, records status values, applies model-specific adapter/battery checks, and only runs a version check for `query` and silent-upgrade modes. Its `version_compare` converts three dot-separated fields to a decimal-like integer; malformed/extra version components and downgrade policy outside those branches are not established. ## PNS event bridge, environment settings and telemetry (static)

`pns_ubus_helper` registers `event_notify(src:int,event:int,detail:string)`, `oneshot_set/get`, `environ_detect_set/get` and `db_detect_set/get`. Its event handler requires `src` and `event`; `src` is bounded 0–5 and dispatches to media-player, alarm, app, other, Mesh and speech sources. Source labels map `0=mp`, `1=alarm`, `2=app`, `3=other[%d]`, `4=mibt mesh`, `5=mdspeech`; source 3 has VoIP/session/mode subevents, but the complete source/subevent map is unknown. Event IDs are bounded at 54. For IDs 0–15, an internal mask (`0x8501`) permits missing/empty detail for IDs 0, 8, 10 and 15; other events require nonempty detail. Source-specific detail checks include PNS start/stop, VoIP on/off, pre-multiround, stop-session, tone status, work-mode change and play-status paths. The full event-ID to business-name dictionary is not recovered.

The producer helper is at VMA `0x119a0`; source/event checks are around `0x1290c` and `0x119d8`; the detail mask is used around `0x11a1c–0x11a24`. It builds a FIFO frame with two 16-bit fields at offsets 0 and 2, then payload from offset 4. Event IDs 4–7 copy a NUL-terminated detail string with length `strlen(detail)+5`; other paths can use a one-byte payload. IDs 17/18 and 50–54 have explicit templates; for IDs 50–53 a detail prefix is compared with the first three bytes of a static string beginning `{"open":[]}`, and the result is serialized as one byte. This is a literal/code fact; the business meaning is unknown. The producer opens `/tmp/mipns/pnshelper.fifo` with `O_WRONLY|O_NONBLOCK` around VMA `0x11bc0` and writes around `0x11d04`, checking partial/error writes.

Static caller examples add limited semantics for selected IDs: `/etc/init.d/pns` sends `src=3,event=0/1` after starting/stopping a speech-engine process, and uses `src=3,event=7/8` for microphone mute/unmute requests. The `service_mute/unmute` caller accepts the helper result only when JSON `code` is zero, then separately synchronizes `mediaplayer.mdplay_action_sync(action=mic_off/on,source=mipns)`; this establishes caller acknowledgement handling and ordering, not a confirmed hardware mute transition. `mic_open` (`src=1,event=0`) also requires integer `code=0` before reporting success and lighting an indicator, while `mic_close` waits six seconds, turns the indicator off and sends `src=1,event=1` without checking the reply. The same script sends these IDs for alarm microphone open/close paths. `/bin/wakeup.sh` brackets a tone playback with `src=3,event=12/13`. `/etc/init.d/wireless` sends `src=5,event=2,detail=on/off` around BLE start/stop. These establish caller-intended labels and ordering only; they do not establish the helper's internal event names or downstream effects beyond the specific caller-side checks.

The `mipns-xiaomi` consumer unlinks the path and calls `mkfifo(path, 0777)` around VMA `0x19d30`, then opens it with `O_RDWR` (flag 2); the requested mode may be affected by process umask and was not measured. Its receive helper at `0x19b58` makes one `read()` call per invocation. It retries only when `read()` fails with `EINTR`, for at most ten attempts; it does not loop to fill a requested buffer. The main loop requests four header bytes at `0x19f24`, requires a return count of exactly four, then loads 16-bit values at offsets 0 and 2. The second field is used as body byte length; a nonzero body is allocated and read in one helper call, and the returned count must equal that length. The first field is bounds-checked against 54 and indexes a 55-entry jump table at `0x1a1f8–0x1a2e0`; many IDs map to a shared unhandled/default branch, while several distinct handlers exist. The consumer therefore interprets the frame as two native little-endian 16-bit fields (`event_id`, `body_len`) followed by `body` on this ARM little-endian target. A short header/body or read error is logged and the current loop proceeds without dispatching the frame; because a short read consumes a prefix from the FIFO, later byte alignment/recovery is not established. Handler semantics for most IDs and whether producer/consumer field values agree for every branch remain open. Separate calls to `write()`/`read()` also mean atomicity and behavior under interleaved producers have not been established. The helper posts bytes through ubus `event` during reads, as direct static evidence; the relationship of those byte notifications to complete-frame delivery is not fully closed.

The shared `environ_detect_get`/`db_detect_get` handler references `/data/mipns/environ_config.json`, reads into a 512-byte buffer and uses embedded default JSON if the read fails. The set path parses JSON then reaches a config event/parser and serialization/write helpers. The current evidence does not prove whether the two ubus methods filter different keys or persist separate schemas. `oneshot_get/set` use `/data/mipns/oneshot` and return/accept JSON through ubus helpers; current data was not read.

Telemetry has a static outbound boundary: `miio_helper` references `upload_stat_points`; the script stages the ROM stat-points log, invokes `matool_collect_stat_points` to produce temporary JSON, runs `statpoints`, then invokes the cleanup script. `statpoints` imports Curl easy APIs and Wi-Fi API URL helpers, and has a `post_stat_points` path with signing/encryption helpers and token/payload placeholders. Its `main` retries a failed post after 10, 20 and 30 second delays when invoked. This establishes an intended local collection→serialization→HTTP POST→cleanup path, not that the post succeeds. The `statpoints_daemon` init file exists but its `START=72` is commented; no active init setting or direct scheduler caller was established, so collection trigger and cadence remain unresolved. The payload fields and their meanings are also unresolved. No log, temporary telemetry file, token, configuration value or user record was read; no collector or upload was executed.

## Method

1. **Census** each init script, executable, shared library, ubus object, local socket, D-Bus interface, config namespace and model/firmware message table. Assign each artifact a role or an explicit “platform plumbing / unknown” classification.
2. **Trace** each product entry point into its handler and downstream calls. Follow caller and callee links across processes; use static disassembly, symbols, strings and code/config relationships as evidence, not as behavior claims.
3. **Recover contracts**: request envelope, field types and bounds, response and error forms, correlation IDs, retries/timeouts, authentication/authorization checks, persistence and observable side effects.
4. **Validate safely** with read-only observation or narrowly reversible tests only where the effect is understood. Do not experiment with raw RPC, credentials, Mesh keys, user databases, external-device controls, pairing, account changes, reset, upgrade or destructive service operations.
5. **Cross-check coverage** by mapping every discovered entry point to one or more ledger rows and every claimed feature to its backing binary/script and evidence. Unknown items remain visible; do not mark the overall goal complete while any feature entry point is unclassified.

The feature ledger is intentionally not yet complete. Initial parallel reviews for physical interaction/power, alarms/notifications/scheduled skills, and connectivity/casting/Line-in are integrated above. Static deep-dives have also added the IR handler contract, Mesh proxy JSON dispatcher, voice privacy/call paths, the 76-script triage, firmware maintenance, and first-pass vendor ELF/dependency/export classifications. The 55-row init-script and 76-row shell-script inventories have both been cross-checked against the local extracted tree. The 169 top-level ELF files still lack a complete caller/role matrix; the 203 dynamic objects, 54 kernel modules and one D-Bus helper still lack a full provider/consumer/loader map. Significant unclassified work remains in the ELF/library graph and feature protocols; do not treat this ledger or its row count as proof that the full ROM has been decoded.

## Nano HTTP TTS endpoint (static ARM analysis)

`etc/init.d/nano_httpd` has `START=96`, skips startup when `micocfg_work_mode` equals `bluetooth`, and otherwise asks procd to run `/usr/bin/nano_httpd` with respawn parameters `3600 5 0`. This is startup-path evidence; it does not establish that the service is active on a particular device.

Static analysis of the stripped ARM EABI5 ELF identifies `getopt` option string `p:d:`. The setup code initializes the default port to `0x22b8` (8888), defaults the work directory to `/tmp/nano_httpd/httpd`, converts the literal `127.0.0.1` using `inet_addr`, then creates/binds/listens on an IPv4 stream socket. The listener is therefore loopback-bound in this binary's default setup; port and work directory can be overridden by the CLI options. No network request was made.

The request parser contains explicit `GET ` and `get ` checks and an error stating only GET is supported. It rejects malformed/incomplete requests and absolute HTTP URIs, then calls `realpath(request_path, NULL)`. The canonical result must compare equal to `/tmp/tts/tts_` for the first 13 bytes; on success the handler opens that exact canonical path with flags `0` (`O_RDONLY`). This establishes a namespace boundary after canonicalization, so a `..` path that resolves outside that prefix is rejected by the comparison. The handler does not derive a FIFO ID from another parameter or append the URL to a separate root: the URL path itself must resolve to the producer's FIFO. Whether encoded path forms are decoded before this check and how callers choose the producer's concrete FIFO name remain unknown. The response template is HTTP/1.0 200 with `Connection: close`; the visible content type is `audio/mpeg3`.

The HTTP handler sends the audio response header, opens the canonical FIFO path read-only, reads up to 32 KiB per chunk, and sends each returned chunk to the client. `alarmd` micmute表项指向 `0x1afe0`，policy `0x232a0` 是 `hour/minute/second` 三个整数字段；缺失值在handler按0处理。`0x1b08c–0x1b0c8` 检查至少一个字段大于0，成立时调用time(NULL)，计算 `now + hour*3600 + minute*60 + second`，作为deadline传入记录构造器 `0x14a94`。因此正值路径按持续时长而非一天中的时分秒处理。该段未见逐字段上下限；全非正值时deadline为0，后续语义未确认。`micmute_remove` (`0x1b1a8`) 调用 `0x13e04`，后者遍历内存记录并对type字段 `+0x10c == 3` 调用移除helper `0x13d14`；尚未闭合即时恢复麦克风的完整路径，不能仅凭remove返回0声称已恢复硬件。未调用接口或读取闹钟数据库。

### Expiry deletion and Line-in sample format follow-up

`mico-helper` 的到期路径 `0x11f88` 先摘链，再经 `0x11cb4` 用节点级别和时间字段构造 `/data/notify/%d/%ld_%ld`，在 `0x11d08` 调用 unlink，最终释放节点及其动态成员。unlink返回值未参与成功判定；删文件失败时内存节点仍被释放，后续重载/恢复未知。`0x11754` 未发现播报调用，不将到期清理描述为到点播报。调度初始化 `0x116f8` 安装1000毫秒uloop timeout；回调 `0x116a4` 取得当前时间，只有difftime严格大于30秒才调用扫描器并更新上次时间，随后再次安装1000毫秒timeout。这不是精确30秒周期，时钟变化和调度延迟的运行结果未知。

转换函数 `0x11ed0–0x11f14` 逐个ldrsh读取有符号16位样本，左移1并在写回前按范围截到16位边界；这支持双倍增益及饱和处理。调用方 `0x1205c–0x12060` 按channels×frames计算样本数。未发现该函数重排/混合声道；尚未把每一条读写缓冲分支与转换函数逐一对应，因此不能声称所有FIFO数据均经过此增益。没有捕获或播放实际音频。

## Alarm recurrence selector and date overrides (static ARM)

`alarmd` 的circle枚举表 `0x372d4` stride8明确对应0=ONCE、1=EVERYDAY、2=WORKDAY、3=MONDAY_TO_FRIDAY、4=HOLIDAY、5=WEEKEND、6=WEEKLY、7=MONTHLY、8=YEARLY。selector `0x12644` 按记录 `+0x10` 的0..8值分派；构造解析分支将6交星期mask解析、7交月日解析 `0x1c430`、8交月日对解析 `0x1c4d4`。这替代此前仅有类别字符串、选择规则未知的部分；完整错误/持久化语义仍需另查。

### TV stream short-read review

独立复核确认首次header read `0x11f88` 请求8字节，只按有符号正返回继续；byte4/5是相对buffer `sp+0x28` 的偏移，均在8字节头内，短读不足6字节时才没有被本次读取完整覆盖。不得把sp+0x2c/+0x2d误算成buffer+12/+13或声称它们超出8字节范围。

后续header read `0x1204c` 的返回在 `0x12068–0x1206c` 经无符号>7分支，-1也会满足该比较；分支随后继续到payload读取，不能当作错误自动退出。payload `__read_chk` 的返回只按是否为零分支，未在该段核对正返回长度与请求长度一致，负返回也非零。后续另有recv排空/状态路径，尚未证明可以补齐前述短读。固定控制包调用前缀生成器时长度值为8，但实际send为24字节，这支持8字节字段表示除16字节前缀以外的长度；其他包型是否同一长度定义仍待逐一核验。全程没有发送包或运行程序。

## IR TX sysfs protocol and allocation mismatch (static candidate)

Local `lib/modules/4.9.61/gpio-ir-tx.ko` SHA-256: `61318c31b9ee8f272d79953875cb0fd2b493183ad143372c4f371cc95aa96f28`. Root and two Luna reviewers independently checked the AArch64 instructions and relocation chain. Probe creates kobject ir_tx_gpio with NULL parent and registers a group; group→attribute relocations lead to name ir_data, mode0644, show=NULL and store callback `.text+0x148`. Successful probe therefore exposes the expected `/sys/ir_tx_gpio/ir_data` write path; actual device module/attribute presence has not been read. The public [kernel sysfs description](https://docs.kernel.org/filesystems/sysfs.html) is used only to interpret the store(buf,count) ABI, not as this ROM's source.

Store saves x3=count and duplicates x2=buf. At `.text+0x190–0x194`, allocation size is `count & 0x3fffffffc` bytes, passed to __kmalloc; there is no multiplication by4. The comma-separated parser `.text+0x1b8–0x1e0` converts each token with simple_strtol(base0) and writes one 4-byte integer at token_index×4 without a capacity check. Only after all writes does `.text+0x1e8` reject an odd token count. Thus input byte allocation and parsed-array byte requirement use different units; sufficiently short tokens can make 4×token_count exceed the allocation. This is a static out-of-bounds-write candidate, not a demonstrated exploit, crash or measured device condition. No test string or write was constructed/executed.

Even token counts enter alternating-index processing: even positions use fixed-point scaling and sendcarrier; odd positions use delay paths, with a 9999 threshold and longer-value loop/remainder handling. The carrier GPIO toggles under spinlock/IRQ-save. Exact pulse units/carrier frequency, numeric bounds, negative-value behavior and userland ir_agent's encoding into this sysfs format remain unresolved; do not send raw data based on this partial contract.
