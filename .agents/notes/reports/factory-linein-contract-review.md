# Report: Factory Line-in contract review

## Scope and evidence

Local ARM static review of extracted `/usr/bin/linein`, init script and `bin/check_linein.sh`. No ROM binary, script, device, audio path or ubus method was executed. No actual ALSA configuration, aux status, player state, user files, identities or credentials were read. The code's fixed command/path literals are evidence of potential reads, not evidence those reads happened in this pass.

ELF SHA-256: `2954f047a13413cca0d6433005304cd9581d887e8ceed3097364ff20bd77fa68`. The first PT_LOAD maps file offset 0 to VMA 0x10000, size 0x368c. The second maps file 0x3ed8 to VMA 0x23ed8. Address evidence below uses these mappings. All 92 ARM PLT slots were independently decoded against their GOT dynamic relocations. Full `.text` disassembly, literal-table decoding and local callsite inspection underpin the bounded entry census.

## Start/stop, PCM and errors

State base0x241f4 holds capture/output pointers at+0/+8, running at+4, tuning word at+0xc and stereo selection at+0x10. Start0x123d0 requires running0, sets running1 before allocations/configuration, builds60-byte PCM structs and selects the worker. Stereo flag0 configures playback `default` plus capture `hw:0,1`, nominal48000/channels2/format2; stereo flag1 skips local playback setup and configures capture nominal44100 with the FIFO worker. Near-setting ALSA APIs may negotiate different values. This is argument evidence, not negotiated hardware readback or full format compatibility proof.

PCM setup0x11c58 returns a negative snd_pcm_open result, but errors from most parameter setters are not tested. Notably snd_pcm_hw_params failure at0x11d98 is logged then returns0 through0x11db4/0x11c84. Thus start can proceed despite a configuration failure and its ubus response does not certify audio readiness. Allocation results are used by memset without explicit null guards in start. Start failure paths call stop0x12358; stop sets running0, requests pthread_join and closes/free-param handles via0x11c00. Struct allocations are retained for reuse. Stop does not restore a separately saved mixer gain or policy in the traced path.

Direct worker0x11f1c reads capture frames, applies fixed signed16 sample doubling with saturation in0x11ed0, and writes ALSA playback. Read errors invoke prepare, other negatives also resume and sleep2000us; write errors invoke prepare or resume→prepare. Positive short writes are not followed by a remaining-tail loop in this worker. Every100 reads it adjusts a64-frame playback correction based on availability/delay. Exact audio clocking correctness, boundaries and error frequencies are unverified. On running0 the direct worker drains output, frees its buffer and returns.

FIFO worker0x12194 allocates period_frames×4 bytes, attempts open(`/tmp/multiroom.fifo`,0x801 = WRONLY|NONBLOCK), retries up to3 times after the first failure with500000us delays, then returns after freeing its buffer if still unsuccessful. It never calls mkfifo and does not prove who creates/reads that FIFO. Open failure returns without visibly clearing running in this worker, so play_status can remain an internal-active flag after worker exit. While running, it reads ALSA, converts samples and calls write with frames×4 at0x12334. The write result is ignored: partial/backpressure/broken-reader effects are not recovered or tested. On normal stop it closes FD and frees its buffer.

## Software-volume connection: bounded negative result

Global0x24188 initializes to1. Exact aligned pointer references are at0x12cbc (getter) and0x12df0 (setter). A full `.text` review of data literals and their address arithmetic found no other traced read into either audio worker: those workers use state base0x241f4, and conversion0x11ed0 loads only fixed saturation bounds and doubles samples. The other direct data bases are ubus context/object/timer, mutex and reply buffer; no reconstructed offset path from those bases to0x24188 was found. This supports **no traced connection from set_soft_vol to PCM gain in this ELF**, not an absolute statement that the entire firmware's effective volume can never change. The handler's call0x12db8 targets the INT32 reply builder and cannot itself be cited as a gain application.

## Acceptance scope and remaining gaps

The extracted-daemon init→main→ubus registration→seven handler ownership chain and bounded direct entry census are now documented. Parent review can use raw table bytes, GOT names and independent callsite inspection as separate evidence. Complete Line-in feature-wide entrypoints still include the kernel AUX detection, physical-control callers and other factory processes; their full triggers, authorization, actual negotiated audio, FIFO consumer/framing, and recovery remain outside this proof. No whole-feature completion is claimed here.

## Player-side AUX and linein control chain (static continuation)

The extracted `/usr/bin/mediaplayer` SHA-256 is `3339a811d8d09c8b5d9ba9f7b6a48a1ae949c76e03b136665e5798c4a12a4a3b`. In its already-linked 43-entry `mediaplayer` object, method `player_aux_operation` maps to handler VMA `0x17354`; the two-field policy is `aux_operation:String` and `aux_tip:Integer`. Handler `0x17354` parses those fields (`0x17374–0x1738c`), converts the operation string and optional integer through local helpers (`0x15c7c`, `0x15cdc`), and dispatches to `mi_aux_operation` at `0x26140`, a tail branch to `aux_operation` at `0x1f3a4` (`0x173bc–0x173c0`). The handler then builds its reply and returns. The operation helper branches on a four-byte prefix equal to `play` (`strncmp` call `0x1f418`); it also has a separate four-byte comparison against the `stop` suffix at `0x38bbc` (`0x1f5bc–0x1f5c8`). This is an operation dispatcher, not a direct call from the handler to the `linein` object's methods. Its state gates include media type/status checks (`0x1f448–0x1f45c`) and an active-player check (`0x1f400–0x1f40c`); the full media transition semantics and the caller's interpretation of the reply remain open.

The player helper `linein_restart` at `0x31890` now has a concrete object/method call trace through `rel_ubus_send` (`0x18474`): it first requires `check_linein` to return nonzero, then `linein_status_get` to return nonzero (`0x31894–0x318a8`). It sends object `linein`, method `stop`, null payload/callback, timeout 100 at `0x318e8–0x318f0`; after that call returns it sends object `linein`, method `start`, null payload/callback, timeout 100 at `0x31930–0x31938`. The first method literal is the `stop` suffix at VMA `0x38bbc`, within the fixed command string `ubus call linein stop` beginning at `0x38bab`; the second is the standalone `start` literal at `0x3717e`. `rel_ubus_send` resolves object ID then invokes the named method (`0x184d4–0x18564`). `linein_restart` does not branch on either invoke result and returns zero on its common path (`0x3193c–0x31944`), so this is a stop/start attempt, not confirmation that either operation succeeded.

Static caller census finds `linein_restart` called from `mi_mdplay_set_status` at `0x26078` and `0x260fc`, and from `mdplay_init` at `0x2a420`. The setter calls occur on its recovered status-change branches; init reaches the helper only under its `type==1 && status==2` branch (`0x2a3cc–0x2a400`). The AUX status initializer `aux_status_init` (`0x31968`) separately calls `check_linein` and `linein_status_get` and posts internal `mdc_process_ind` events; its call path is not evidence that a user control request succeeded. Fixed player strings include `ubus call linein start`, `ubus call linein stop`, `ubus ... linein.play_status`, and `ubus ... linein.line_status`; only the `linein_restart` `rel_ubus_send` path above is tied here to exact object/method arguments.

This closes a static player-to-linein control edge and the `player_aux_operation` owner/handler edge, but not the physical event device mapping, all AUX event producers, touchpad's runtime ubus destination/argument bytes, player mode meanings, or successful audio recovery. No ubus request, media operation, ROM code, script, module or device was executed.

### Entry-census verification details

The full disassembly contains202 direct BL instructions and no SVC instruction; all92 PLT slots resolve to imported names. The only MOVW instructions construct flags0x801, rates48000/44100 and a period literal0x372; no MOVT-based global address construction was found. Exact literal and arithmetic review covered the gain word plus all daemon state, ubus context/object/timer, mutex and blob-buffer bases. This corroborates the bounded no-additional-direct-listener and no-traced-gain-reader findings; it is not a syscall/runtime monitor of the process or its shared libraries.

The get_soft_vol placeholder policy bytes are exactly `(name_pointer=0,type=0)`, not a named empty-string field. Its count remains1 in method metadata, while the handler decodes no argument. The reconnect timer at0x2418c stores callback0x12cc4 at+0xc. The sole local init-array target0x11bfc is a return stub; diagnostic helper0x11e00 has no exact embedded function-pointer reference in this ELF in addition to no direct call.
