## 六、方舟文本链路（补测）

用户随后提供了方舟 API Key 与模型 `doubao-seed-2-1-lite-260915`。

- 鉴权确认：先用不存在的模型名探测，返回 HTTP 404（模型不存在）；Key 无效才会是 401。说明鉴权通过。
- `POST /api/v3/chat/completions`（既有客户端）：`http_status=200`、`ark_completion_shape_valid=1`，32 token 上限内返回有效 `choices/message/content`。
- `POST /api/v3/responses`（新增 `--responses` 模式，不流式、`max_output_tokens=256`）：`http_status=200`、`ark_responses_shape_valid=1`，返回 `output[0]=reasoning`、`output[1]=message`，消息文本长度 2。
- 发现：该模型默认先产出 `reasoning` 项。把 `max_output_tokens` 设为 32 时，推理项耗尽预算，只有 reasoning、没有 message，验证失败；调到 256 后正常。做 Harness 时需要给推理预留 token，或显式关闭/调低思考。
- 这也回答了之前的疑问：文本模型会把推理作为结构化 item 暴露；实时语音协议的文档里没有对应的思维链事件。
- 客户端只打印结构（item 类型与文本长度），不打印生成内容；日志 `logs/ark-auth-smoke.txt`。

结论：语音与文本两个服务都已用真实 Key 验证可用，文本侧可以作为 Harness 后端。
