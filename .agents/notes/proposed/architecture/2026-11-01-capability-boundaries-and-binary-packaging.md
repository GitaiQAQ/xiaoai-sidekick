# Agent Note: 能力边界与二进制打包

Status: proposed

## Problem

当前网易云与工具执行编入 Web 程序，语音 Agent 经本机 socket 调用。未来加入米家、灯光、命令执行等能力时，继续把业务实现直接加入 Web 或 Agent，会让入口、编排与能力相互依赖；但每个能力都拆成独立程序或常驻服务，也可能增加存储、内存、部署与维护成本。

设备资源有限，模块独立、二进制独立和进程独立应分别决策。现有实现与背景见[项目上下文](../../reference/context.md)。

## Proposal

本提案暂不实施，不拆分现有二进制、不新增服务、不改变部署。后续设计沿用以下约定，随实际功能开发逐步形成边界，尽量避免额外改造、重复实现与无需求的基础设施。

- Web 负责展示与交互；Agent 负责会话、模型与工具编排；网易云、米家、灯光等各自承担能力实现。能力提供明确接口，不依赖 Web 页面或特定模型。Web、Agent 及未来原厂小爱请求分流可以复用能力。
- 新增米家等能力时，将协议、认证、设备操作封装在独立代码模块中，不直接散入 Web 路由或 Agent 循环。入口只做适配、参数校验和调用。模块独立不要求独立 bin。
- 允许多个模块合编成一个二进制。若实际构建证明合编产物更小，且满足运行、可选功能及维护需求，优先合编；保留能力接口，不以拆文件数量作为目标。
- 独立 CLI 是可选调用形式，需要脚本使用、独立启停或故障隔离时再增加。可以复用同一能力库，也可以采用一个二进制的多个子命令，避免复制实现。
- 不默认每项能力常驻。只有持续状态、并发访问或延迟要求确实需要时才考虑服务与本机 IPC。音频帧处理等高频路径保持在常驻进程内，不逐次启动 CLI。
- 安装包与二进制数量分开考虑：即便多个程序，也可以统一发布一个安装包。暂不设计插件加载器、通用能力守护进程或新的 RPC 框架。

后续可选形态包括“少量常驻进程 + 按需 CLI + 共用能力库”，以及“模块合编 + 子命令入口”；当前不锁定其中一种。

## Acceptance criteria

- 本轮只记录提案，未改程序、构建或设备。
- 后续新增能力有清晰的业务接口；Web 与 Agent 不各写一份协议与认证逻辑。米家等模块可在不依赖页面或模型会话的情况下调用。
- 决定增加 bin、服务或合并程序前，针对实际需求比较完整部署文件的总字节数、运行内存、启动延迟、状态管理与维护成本；记录实测结果，不以“合编必然更小”或“拆分必然更省”为事实。
- 若合编体积更小且其他约束满足，允许并优先选择合编；若选择拆分，应给出具体收益。不为证明提案主动启动重构或基准项目。

## Risks

合编可能使模块边界再次被入口侵入，也会耦合发布与故障范围；拆分可能重复链接公共代码，增加启动、IPC 和状态同步成本。产物大小受链接方式、裁剪与资源打包影响，当前尚无同等功能方案的体积对比实测。

命令执行能力需要定义参数及授权边界，不能把模型输出直接拼成 shell 命令。具体方案随该能力设计，不在本提案中新增执行机制。

## Alternatives considered

- 所有能力直接堆入一个程序：可能节省体积，但放弃业务边界会阻碍复用。保留合编选项，要求模块隔离。
- 每个能力各一个 CLI 或常驻服务：组合灵活，但当前收益不足以支持统一拆分，且可能增加资源和运维开销；仅按需求采用。
- 现在就拆出网易云和工具执行：先前讨论过，但用户明确暂不实施；留到相关功能变更时再评估，以减少额外改造。
